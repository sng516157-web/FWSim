# M8 — Node Workbench (platform builder + control design)

- **Date:** 2026-11-06
- **Stage file:** `Milestones/M8_node_workbench.md`
- **Builds on:** M7 pipeline hooks, M6.75 live sessions, M6 closed-loop demo

## 1. Pipeline executor (Task 0) — `control/pipeline.py`

YAML schema `pipeline: [{id, type, params, inputs: [{port, from}]}]`;
topo-sorted dataflow executor compiles to `pipeline(state, t) -> dict`.
Typed ports (`state / imu / mocap / channels / torque / scalar`); every
wiring error — unknown type, unwired required port, unknown port, unknown
block reference, type/shape mismatch, cycle — raises `PipelineError` at
LOAD, never mid-run.

Design decision surfaced by tests: `state`-signal input ports are
**executor-injected** (the plant state) unless explicitly wired. That is
what makes the S3 contract structural: a controller wired to
`estimator.state` sees the estimated state; the wiring decides, not block
internals (the LQR block ignores its raw `state` argument — pinned by
test).

## 3. Node editor (Task 2) — `ui/nodes/`

Custom QGraphicsScene (the survey-consistent choice — we already own
PySide6; NodeGraphQt was rejected in planning as a maintenance risk).
Two canvases per the design rules: pipeline DAG (`pipeline_canvas.py`) with
typed ports — connections are checked against the BLOCK_REGISTRY at
drag-release and rejected visibly; platform tree (`platform_tree.py`).
Graph ops are Qt-free (`PipelineGraph`, `PlatformTree`) and tested
offscreen; rendering is the human check. The GUI's "nodes" tab hosts both
editors; the pipeline editor has an add-block toolbar and a
compile-then-save action (invalid graphs are rejected, not saved).

## 4. Platform builder (Task 3) — `vehicle/platform_builder.py`

Tree editor core: bodies → joints → wings, with URDF import as a node
source (M6.75 importer) and hand-added wing blocks. Compiles to the SAME
verbose vehicle YAML with provenance blocks (design rule 1); export
validates through the schema before writing. Workflow: import URDF →
attach wings → save → run.

## 5. Pipeline-driven hover demo (Task 4)

`experiments/m8_pipeline_hover.yaml` + `experiments/m8_hover_pipeline.yaml`:
IMU + mocap → complementary estimator → altitude PID + attitude PID →
summer → wingbeat mixer → free-body plant (`pipeline:` field on the
experiment; `FreeBodyPlant.attach_pipeline` evaluates the DAG once per
wingbeat, A-007, mixer deltas applied from baseline kinematics so commands
do not accumulate). Channel commands recorded as `control_channels` in the
run record.

### Result (honest)

The pipeline machinery works end to end: the run completes (`status: OK`),
channel commands are evaluated once per wingbeat, applied through the mixer
from baseline kinematics, and recorded as `control_channels`.

The demo does NOT stabilize hover. Measured on
`outputs/20261106_131442_m8_pipeline_hover` (15 wingbeats, 1 s):

| quantity | value |
|---|---|
| z (NED down) | 0 → +2.39 m (vehicle sinks) |
| pitch | 0.05 → −1.36 rad (attitude diverges) |
| thrust channel | saturates at +0.30 (mix limit) from beat ~3 |
| pitch channel | ~0 throughout (no authority) |

Diagnosis (three compounding causes):
1. **No thrust margin.** The baseline kinematics produce 0.935× weight at
   hover (measured, fixed-body); even the +30% mixer cap leaves <1.6×
   weight, and pitching over tilts the lift vector away from vertical.
2. **Pitch channel has ~no moment authority on this geometry.** Gain sweeps
   (kp 0.02 → 20, kd 0.05 → 40) change the outcome by <5%: a pitch_offset
   shift on both wings produces almost no pitch torque here.
3. **Hand-tuned PIDs on an open-loop-unstable plant** (M6's central
   finding) without trim/linearization — the deferred proper fix is LQR on
   a linearized Level-2 plant.

vs the M6 truth-state loop: M6's LQR-on-trim stabilizes the Level-1
reduced model; M8 shows the pipeline infrastructure on the Level-2 plant
with the controller on the ESTIMATED state (S3 honoured structurally),
but stabilization needs a designed controller, not canned PID gains.
